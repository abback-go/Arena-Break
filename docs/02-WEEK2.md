# 2-1. 설계 논의 — 코드를 쓰지 않는 25분 (25분)

> **오늘의 핵심 활동입니다.** 오늘 3시간 중 이 25분이 나머지 155분을 결정합니다.

## 왜 코드를 안 쓰는가

지금부터 만들 것은 **서로 물려 있습니다.**

```
총알이 적을 맞힌다        → 적이 데미지를 받는다
적이 플레이어를 때린다     → 플레이어가 데미지를 받는다
적이 죽는다              → 웨이브가 그것을 안다
웨이브가 다 끝난다        → 게임이 그것을 안다  (3주차)
```

여기서 **"데미지를 받는다"가 두 번 나옵니다.** 플레이어와 적, 서로 다른 클래스입니다.
지금 아무 생각 없이 만들면 `WeaponSystem` 안에 이런 코드가 생깁니다.

```csharp
// 이렇게 되면 안 된다
if (hit.collider.GetComponent<EnemyAI>() != null) { ... }
else if (hit.collider.GetComponent<PlayerController>() != null) { ... }
```

적 종류가 늘 때마다 `WeaponSystem` 을 고쳐야 합니다. **1주차에 배운 "한 클래스는 하나의 책임"이 깨집니다.**

## 프롬프트 (그대로 붙여넣기)

```
체력/데미지 시스템을 만들 건데, 먼저 설계부터 논의하자. 코드는 아직 쓰지 마.

플레이어와 적이 같은 방식으로 데미지를 받게 하고 싶어.
IDamageable 인터페이스와 Health 컴포넌트로 나누는 게 좋을까?

사망 처리, 무적 시간, 체력 변화 이벤트를 각각 어디에 두는 게 좋을지
2~3가지 안을 장단점과 함께 제시해줘. 결정은 내가 한다.
```

## 이 프롬프트의 핵심

| 줄 | 역할 |
|---|---|
| **"코드는 아직 쓰지 마"** | 이 한 줄이 없으면 AI가 바로 파일을 만듭니다 |
| "2~3가지 안을 장단점과 함께" | 선택지를 강제로 꺼냅니다 |
| **"결정은 내가 한다"** | AI가 하나를 골라주고 넘어가는 것을 막습니다 |

이 패턴의 이름: **논의 → 결정 → 구현**

## 무엇을 결정해야 하는가

답이 나오면 아래 4개에 **본인의 답**을 적으세요. 정답은 없습니다. 근거가 있으면 됩니다.

```
1. IDamageable 에 들어갈 메서드는?           (예: TakeDamage(int amount))
2. 죽었을 때 누가 처리하나?                   Health 인가, 각 객체(EnemyAI)인가
3. 체력이 변할 때 UI는 어떻게 아나?            event 인가, 폴링인가
4. 무적 시간(피격 직후 잠깐 무적)은 넣나?      넣는다면 어디에
```

3번은 이미 `CLAUDE.md` 에 답이 있습니다. 열어서 확인하세요.

> **UI는 폴링하지 말고 C# event 구독으로 갱신할 것**

이렇게 **규약이 설계 결정을 미리 해두는 것**이 `CLAUDE.md` 를 쓰는 이유입니다.

## 프롬프트 (그대로 붙여넣기)

**아래 프롬프트는 하나의 예시입니다.** 2-1에서 다른 안을 골랐다면 그 안에 맞게 고쳐 쓰세요.

```
방금 논의한 설계대로 체력 시스템을 만들어줘.

- IDamageable: TakeDamage(int amount) 하나만 가진 인터페이스
- Health: IDamageable을 구현하는 MonoBehaviour
  - 최대 체력은 인스펙터에서 조절, 기본 100
  - 현재 체력은 밖에서 프로퍼티로 읽기만 가능하되,
    플레이 중 인스펙터에서 값이 보이게 할 것 — 눈으로 검증해야 한다
  - 체력이 변하면 event로 (현재, 최대) 를 알릴 것
  - 0 이하가 되면 사망 event를 한 번만 발생시킬 것 (여러 번 맞아도 한 번)
  - 죽은 뒤에는 더 이상 데미지를 받지 않을 것
```

### 왜 "파괴는 Health가 하지 않는다" 인가

적은 죽으면 1초 뒤 사라져야 하고, 플레이어는 죽어도 사라지면 안 됩니다(게임오버 화면을 봐야 함).
**같은 `Health` 를 둘 다 쓰려면 파괴 정책을 밖으로 빼야 합니다.**

이것이 2-1에서 논의한 "사망 처리는 누가 하나"의 실제 결과입니다.

## 검증 — 표적으로 확인합니다

1주차에 만든 표적 3개를 그대로 씁니다. MCP로 `Health` 를 붙입니다.

```
Target_1 / Target_2 / Target_3 에 Health 컴포넌트를 붙여줘.
최대 체력은 30으로 설정.

끝나면 세 오브젝트의 Health 값을 다시 읽어서 실제로 30이 들어갔는지 보여줘.
```

> `Health` 가 안 붙으면 네임스페이스 전체 이름(`ArenaBreak.Core.Health`)이 필요합니다.
> 1주차 `PlayerController` 때와 같은 함정입니다.

`Hierarchy` 에서 `Target_1` 을 **선택해 둔 채로** Play 를 누르세요.
`Inspector` 의 `Current Health` 가 실시간으로 줄어드는 것이 보입니다.

```
□ 표적을 1번 쏘면 Current Health 가 30 → 20 이 된다
□ 3번 쏘면 0이 된다
□ 0이 된 뒤 더 쏴도 음수가 되지 않는다
□ 벽을 쏘면 에러 없이 구체만 생긴다
□ 콘솔에 에러가 없다
```

> **Play 전에는 `Current Health` 가 0으로 보이는 것이 정상입니다.**
> `Awake()` 에서 최대 체력으로 채우기 때문입니다. Play 를 누르면 30이 됩니다.

표적은 죽어도 **사라지지 않습니다.** `Health` 가 파괴를 하지 않도록 만든 설계라 정상입니다.
사라지게 만드는 것은 2-3의 `EnemyAI` 가 합니다.

# 2-3. 적 AI (45분)

## 프롬프트 (그대로 붙여넣기)

```
NavMeshAgent 기반 근접 적을 만들어줘.

요구사항:
- 상태는 Idle / Chase / Attack / Dead — enum + switch로 단순하게.
  상태 머신 프레임워크나 별도 클래스를 만들지 마
- 플레이어를 추적. 추적 시작 거리와 공격 거리는 인스펙터에서 조절
  (기본: 추적 60m, 공격 2m)
- 공격은 2초 간격, 데미지 10. 앞서 만든 IDamageable로 줄 것
- 체력은 앞서 만든 Health 컴포넌트를 쓴다. EnemyAI가 체력을 따로 갖지 마
- Health의 사망 event를 구독해서 Dead 상태로 가고, 1초 뒤 오브젝트 파괴
- 구독한 event는 OnDisable에서 반드시 해제할 것
- 플레이어는 태그가 아니라 [SerializeField] Transform 참조로 받을 것
  (씬에 하나뿐이지만, 매 프레임 Find 하지 않기 위해)
- 단, 이 적은 프리팹으로 만들어 웨이브가 스폰할 것이다.
  프리팹은 씬 오브젝트를 참조할 수 없으니, 스폰한 쪽이 플레이어를 넣어줄 수 있게
  공개 메서드를 하나 둘 것

파일: Assets/Scripts/Enemy/EnemyAI.cs 하나만 생성.
씬과 프리팹은 건드리지 말고 세팅 절차만 알려줘.
```

### 이 프롬프트에서 지정한 것들

| 지정한 줄 | 없으면 생기는 일 |
|---|---|
| "enum + switch로 단순하게" | 상태 하나에 클래스 하나씩, 파일 5개짜리 프레임워크가 나옵니다 |
| "Health 컴포넌트를 쓴다" | `EnemyAI` 안에 `_hp` 필드가 또 생겨 체력이 두 군데가 됩니다 |
| "OnDisable에서 해제" | `CLAUDE.md` 규약이지만 **한 번 더 씁니다.** 이건 안 지켜지면 메모리 누수입니다 |
| "태그가 아니라 Transform 참조" | `GameObject.FindWithTag` 가 `Update()` 에 들어갑니다 |
| "스폰한 쪽이 넣어줄 공개 메서드" | 이게 없으면 **2-4에서 스폰된 적이 전부 제자리에 서 있습니다** |

### 프리팹은 씬 오브젝트를 참조할 수 없습니다 ★

인스펙터로 플레이어를 연결하는 방식은 **손으로 놓은 적 1마리에만 통합니다.**
프리팹 에셋은 씬에 있는 `Player` 를 가리킬 수 없습니다. 씬이 바뀌면 그 참조가 무의미해지기 때문입니다.

그래서 프리팹의 플레이어 칸은 **비어 있는 것이 정상**이고, 스폰하는 쪽(2-4의 `WaveSpawner`)이
스폰 직후에 넣어줘야 합니다.

> 이 제약을 모른 채 2-4까지 가면 "적이 스폰은 되는데 안 움직인다"로 30분을 씁니다.
> **에셋과 씬의 경계**는 Unity에서 가장 자주 밟는 함정입니다.

| 값 | 어디서 나왔나 |
|---|---|
| `Stopping Distance` **1.8** | 공격 거리가 2m입니다. 이보다 크면 적이 사거리 밖에 멈춰 **영원히 공격하지 않습니다.** 0이면 플레이어 몸에 파고들어 밀어냅니다 |
| 추적 거리 **60m** | 아레나가 40×40이라 **대각선이 약 57m** 입니다. 이보다 작으면 먼 구석에 스폰된 적이 가만히 서 있고, 플레이어가 다가가야만 움직입니다 |

> **두 값 다 짐작이 아니라 다른 수치에서 나온 값입니다.**
> 공격 거리를 바꾸면 `Stopping Distance` 를, 아레나 크기를 바꾸면 추적 거리를 같이 봐야 합니다.
>
> **매직 넘버 금지**가 `CLAUDE.md` 에 있는 이유가 이것입니다. 근거 없는 숫자는 나중에 왜 그 값인지 아무도 모릅니다.

### 왜 Transform 배열을 안 쓰나 ★

프롬프트에서 **"Transform 배열을 인스펙터에 노출하지 마"** 라고 못박은 이유가 있습니다.

**MCP는 씬 오브젝트 참조 배열을 채우지 못합니다.** 웨이브 리스트(`WaveData` 에셋)는 잘 들어가는데,
`Transform[]` 은 성공 메시지만 뜨고 값은 전부 `None` 으로 남습니다.

| 넣는 것 | MCP로 되나 |
|---|---|
| 에셋 참조 (프리팹, ScriptableObject, 머티리얼) — 단일·배열 모두 | ✅ |
| 씬 오브젝트 참조 — **단일** 칸 | ✅ |
| 씬 오브젝트 참조 — **배열·리스트** | ❌ 성공이라고 답하지만 비어 있음 |

그래서 부모 오브젝트 **하나만** 받고 자식은 코드에서 모읍니다.
덤으로 스폰 위치를 늘려도 인스펙터를 다시 연결할 필요가 없습니다.

> **도구의 한계가 설계를 바꾼 사례입니다.**
> "성공했습니다"를 믿고 넘어갔다면 Play 했을 때 적이 한 마리도 안 나왔을 것입니다.
