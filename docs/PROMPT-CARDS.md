# 프롬프트 카드

수업에서 사용하는 검증된 프롬프트 모음입니다.
**그대로 복사해서 쓰는 것이 목적이 아닙니다.** 각 카드가 왜 이렇게 쓰였는지 이해하고, 과제에서는 직접 작성하세요.

---

## 좋은 프롬프트의 5가지 조건

1. **무엇을** 만들지 한 문장으로 먼저 말한다
2. **요구사항을 항목으로** 나열한다 (숫자·단위까지)
3. **파일 경로를 지정**한다 — AI가 파일을 흩뿌리는 것을 막는다
4. **하지 말아야 할 것**을 명시한다 ("씬은 건드리지 마", "PlayerController는 수정하지 마")
5. **한 번에 하나씩** 요청한다

> 프롬프트를 쓰는 데 3분을 쓰면, 결과를 고치는 데 30분을 아낍니다.

# 1주차

## 카드 #1 — 플레이어 이동

```
1인칭 플레이어 컨트롤러를 만들어줘.

요구사항:
- Input System(신규) 사용, CharacterController 컴포넌트 기반
- WASD 이동, 마우스 시점 회전(상하 각도 -80~80도 제한), Space 점프
- 이동 속도 / 마우스 감도 / 점프 높이는 인스펙터에서 조절 가능
- 카메라는 자식 오브젝트로 두고 상하 회전만 담당
- 중력 직접 적용

파일: Assets/Scripts/Player/PlayerController.cs 하나만 생성.
씬은 건드리지 말고, 내가 직접 붙일 테니 필요한 세팅 절차만 알려줘.
```

**이 카드의 포인트**
- "CharacterController 기반"으로 구현 방식을 못 박았다 → Rigidbody 방식과 섞이지 않는다
- 각도 제한 수치를 줬다 → 목이 뒤로 꺾이는 버그를 사전 차단
- "파일 하나만" + "씬은 건드리지 마" → 범위를 강제로 좁혔다

---

## 카드 #2 — 사격

```
Raycast 기반 사격 시스템을 추가해줘.

요구사항:
- 좌클릭 발사, 발사 간격 0.15초, 사거리 50m
- 명중 지점에 디버그용으로 작은 구체를 0.5초간 표시
- 탄약 12발, R키 재장전(1.5초, 재장전 중 발사 불가)
- 카메라 정중앙에서 Ray를 쏠 것
- PlayerController는 수정하지 말고 별도 컴포넌트로

파일: Assets/Scripts/Player/WeaponSystem.cs
```

**이 카드의 포인트**
- "PlayerController는 수정하지 마" → 한 클래스가 비대해지는 것을 막는다
- 디버그 표시를 요구했다 → 눈에 보여야 검증할 수 있다

## 비교 실험 — 나쁜 프롬프트

```
총 쏘는 기능 만들어줘
```

수업 중에 이것도 한 번 돌려봅니다. 결과를 카드 #2와 비교해 보세요.

**무엇이 달라지는지 직접 확인할 것:**
- 파일이 몇 개 생겼는가?
- 요청하지 않은 기능이 붙었는가?
- 수치가 어디서 왔는가?
- 씬을 건드렸는가?

> **결론: 명세를 쓰는 능력 = AI 활용 능력**

# 2주차

## 카드 #3 — 설계 우선 (코드를 쓰기 전에)

```
체력/데미지 시스템을 만들 건데, 먼저 설계부터 논의하자. 코드는 아직 쓰지 마.

플레이어와 적이 같은 방식으로 데미지를 받게 하고 싶어.
IDamageable 인터페이스와 Health 컴포넌트로 나누는 게 좋을까?
사망 처리, 무적 시간, 체력 변화 이벤트를 어디에 두는 게 좋을지
2~3가지 안을 장단점과 함께 제시해줘.
```

**이 카드의 포인트**
- **"코드는 아직 쓰지 마"** ← 이 한 줄이 핵심이다
- 선택지를 요구하고, **결정은 사람이 한다**
- 이 패턴의 이름: **논의 → 결정 → 구현**

## 카드 #4 — 적 AI

```
NavMeshAgent 기반 근접 적을 만들어줘.

- 플레이어를 추적, 2m 이내면 공격 (2초 간격, 데미지 10)
- 앞서 만든 IDamageable을 구현할 것
- HP 30, 사망 시 1초 뒤 파괴
- 상태: Idle / Chase / Attack / Dead — enum + switch로 단순하게
- 값은 전부 SerializeField

파일: Assets/Scripts/Enemy/EnemyAI.cs
NavMesh 베이크는 내가 할 테니 절차만 알려줘.
```

**이 카드의 포인트**
- "enum + switch로 단순하게" → 요청하지 않은 복잡한 상태 머신 프레임워크를 막는다
- "앞서 만든 IDamageable을 구현할 것" → 기존 코드와의 연결을 명시

## 카드 #5 — 데이터 주도 설계

```
ScriptableObject 기반 웨이브 시스템을 만들어줘.

- WaveData(ScriptableObject): 적 프리팹, 스폰 수, 스폰 간격
- WaveSpawner: WaveData 리스트를 순서대로 진행,
  현재 웨이브의 적이 전멸하면 3초 후 다음 웨이브
- 스폰 위치는 씬에 배치한 Transform 배열 중 랜덤
- 웨이브 시작 / 클리어 / 전체 클리어를 C# event로 노출

파일 2개만: Core/WaveData.cs, Core/WaveSpawner.cs
오브젝트 풀링은 아직 넣지 마. 다음 단계에서 할 거야.
```

**이 카드의 포인트**
- **"오브젝트 풀링은 아직 넣지 마"** → 다음 단계를 위해 일부러 남겨둔다
- 한 번에 완벽하게 만들지 않는 것이 오히려 안전하다

## 카드 #5b — 리팩터링

```
방금 만든 WaveSpawner에 오브젝트 풀링을 적용해줘.
Instantiate/Destroy를 풀 재사용으로 바꾸되,
WaveSpawner의 공개 API와 event는 그대로 유지할 것.
변경 전후 차이를 요약해서 설명해줘.
```

**이 카드의 포인트**
- **"공개 API와 event는 그대로 유지"** → 이것이 리팩터링의 정의다
- "변경 전후 차이를 설명해줘" → 리뷰 없이 넘어가지 않는다

```
게임 상태 머신과 HUD를 만들어줘.

GameManager: Ready → Playing → WaveClear → GameOver → (재시작)
```

## 카드 #7 — 게임필 (한 번에 하나씩)

```
타격감을 넣어줘. 단, 한 번에 하나씩 하고 매번 내가 테스트할게.
1) 머즐 플래시 + 명중 파티클
2) 피격 시 카메라 셰이크 (0.1초, 강도 조절 가능)
3) 적 피격 시 머티리얼 0.05초 흰색 플래시

1번부터 시작해.
```

**이 카드의 포인트**
- 할 일을 다 보여주되 **"1번부터"** 로 실행을 제한했다
- "매번 내가 테스트할게" → 검증 주체를 명시

## 카드 #8 — AI 코드 리뷰 ★이 수업의 클라이맥스

```
지금까지 작성된 Assets/Scripts 전체를 리뷰해줘.

다음 관점으로 문제를 찾아 심각도 순으로 정리:
- Update()에서의 불필요한 연산 / GetComponent 호출
- null 참조 가능 지점
- event 구독 후 해제 누락 (메모리 누수)
- 책임이 뒤섞인 클래스
- CLAUDE.md 규약 위반

각 항목마다 파일:줄 번호와 수정 방향을 제시하되, 아직 고치지는 마.
```

**진행 방법**

1. 리뷰 결과를 그대로 믿지 말고 **하나씩 코드를 열어 확인**한다
2. **틀린 지적을 최소 1개 찾아낸다** — 실제로 섞여 나옵니다
3. 우선순위 3개만 골라 수정을 지시한다
4. 수정 후 다시 플레이 테스트한다

> **AI의 리뷰도 검증 대상입니다.**

# 막혔을 때 쓰는 프롬프트

## 에러가 났을 때

```
컴파일 에러가 났어. Unity 콘솔을 읽고 원인을 설명해줘.
바로 고치지 말고, 왜 이 에러가 났는지 먼저 알려줘.
```

## 코드가 이해 안 될 때

```
방금 만든 <파일명>을 한 블록씩 나눠서 설명해줘.
내가 Unity를 배운 지 얼마 안 됐다고 생각하고,
"왜 이렇게 짰는지"에 초점을 맞춰서.
```

## 동작이 이상할 때

```
<증상>이 발생해. 예상 동작은 <기대>인데 실제로는 <실제>야.
원인 후보를 3개 제시하고, 각각을 어떻게 확인할 수 있는지 알려줘.
추측으로 고치지 말고 확인 방법부터.
```

## 되돌리고 싶을 때

프롬프트가 아니라 Git으로 해결합니다.

```bash
git checkout .              # 마지막 커밋 이후 변경 전부 취소
git checkout -- <파일경로>   # 특정 파일만 취소
```

> **3회 시도해도 안 되면 되돌리세요.** 무한 루프에 시간을 쓰지 마세요.

# 내 프롬프트 기록하기

과제 제출 시 **사용한 프롬프트 전문**을 함께 냅니다.
`docs/my-prompts.md` 파일을 만들어 아래 형식으로 기록하세요.

```markdown
## 2주차 과제 — 원거리 공격 적 추가

### 시도 1
(프롬프트 전문)

**결과**: 기존 EnemyAI를 수정해버림 → 실패
**원인 분석**: "기존 EnemyAI를 수정하지 말라"는 제약을 안 썼다

### 시도 2
(수정한 프롬프트 전문)

**결과**: 성공
**배운 점**: 하지 말아야 할 것을 명시하는 게 요구사항보다 중요할 때가 있다
```

**실패한 시도를 지우지 마세요.** 실패 기록이 회고 점수의 근거가 됩니다.
